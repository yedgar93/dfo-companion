# Portable companion feasibility and validation

The portable deliverable is one `DFO-Companion.mjs` file, run with Node.js22.15 or newer. It combines the reader, dashboard server, dashboard code, styles, fonts, reference pictures, licenses, and reviewed-version metadata. It does not require npm packages on the user's machine. It does not contain the DFO executable or original game data.

Runtime artwork decoded from the user's own game is cached per user: `%LOCALAPPDATA%/DFOCompanion/paperdoll` on Windows, `~/Library/Caches/DFOCompanion/paperdoll` on macOS, and `$XDG_CACHE_HOME/DFOCompanion/paperdoll` (or `~/.cache/DFOCompanion/paperdoll`) on Linux. `DFO_COMPANION_CACHE` can override the parent cache directory. This cache is disposable and is not a second executable or feeder process.

## Starting the portable file

Run `node DFO-Companion.mjs` to start only the companion, or add `--open` to open its dashboard window. When the game is not running, Windows or macOS users may explicitly run `node DFO-Companion.mjs --launch-game --open` to start the unchanged official game with the required loopback flags and open the dashboard. Use `--game-path "D:/Games/DFO Online/DFO Online.exe"` for another installation location. Startup refuses to launch a duplicate game and refuses to proceed if the process check fails. This command never modifies a shortcut, game binary or updater file. On macOS the companion checks `/Applications/DFO Online.app` and `~/Applications/DFO Online.app`, reads the bundle’s `CFBundleExecutable`, and also accepts `--game-path "/Applications/DFO Online.app"`. Windows and macOS startup both refuse duplicates and use the same loopback-only diagnostic flags. macOS discovery and launch behavior have automated mock coverage; actual Mac runtime has not been tested on this Windows machine. Linux requires manual official-game startup with the flags.

## Connection requirement

An ordinary launch of the current official game does not expose a supported external live-character API. The installed0.1.10435 Electron main and preload sources were inspected without launching or changing the game. Main source supports Chromium's explicitly supplied remote-debugging flag; it does not start a read-only companion listener automatically. The isolated preload exposes local storage, update notification and pointer-lock functions, not an external live-character service.

Therefore the portable companion can connect to a game already started with the local diagnostic endpoint. It cannot safely add startup flags to an existing process. A true normal-launch, no-flags connection requires a supported game API or a developer-provided integration. The companion must explain this state and wait; it must not silently restart or modify the game.

Game updates remain fail-closed: an unreviewed loaded version is not automatically accepted. Updating or restarting cannot bypass source review. Authorized phone access uses a separate server bound to one private IPv4 address on port9235. The phone must be on the same subnet and open the temporary pairing link shown in Connection on the computer. Pairing links last10minutes; paired read-only browser sessions last8hours. The phone reads the same cached dashboard; it does not open another game reader. The game diagnostic endpoint stays loopback-only. The platform-neutral .mjs still needs Node22; the optional Windows .exe embeds its runtime and requires no Node installation. The Windows executable opens only the dashboard. macOS runtime remains untested on this Windows machine.

Current source identities: main.cjs SHA256 `a3cf12293d9d35a1ace71887f2ce914710e4dc07a957ca14561ab0e49f2bf20b`; preload.cjs `d575a65ecef649101f83b3774f3a606cc32ebc4423a22e447459040f7150aba4`. The current source explicitly documents retaining support for `--remote-debugging-port`.

## Build and self-checks

`work/build-portable.mjs` uses a development-only esbuild0.25.12 installation from the npm registry. Static resources are embedded directly; no external font or image requests occur at runtime. Build output requires no bundler. Imported development command-line guards are removed during bundling, preventing extra observers from starting.

`node DFO-Companion.mjs --check-bundle` validates embedded review metadata and dashboard resources without connecting to the game. `--check-bundle-http` serves and checks embedded frontend assets on a temporary loopback test port, using a fake sampler and no game reads. A copied file in an otherwise empty directory is used for portability checks.

## Performance diagnostic limitation

A passive12-second companion-on/off comparison collected only Chromium Performance counters. Renderer task time remained high in both windows (on91.5%, off95.6%); script time was64.5% on and88.7% off. The game continued normally and was not paused or controlled. These uncontrolled windows do not identify the cause of lag and do not exclude short debugger-induced stalls. Counters measure task/script occupancy, not frame rate. The deployed single-file warm-reader test subsequently recorded8new readings in30seconds, with update gaps3.267–4.785seconds. Its source-read counter stayed28 and debugger-enable counter stayed1 while fast-read count increased27→35. The copied own-player data took0.4–0.7milliseconds inside the renderer; the full protocol read took approximately1.5seconds. These results verify review reuse and bounded copying, not that rendering or multiplayer lag is fixed. Raw evidence: `work/portable-warm-performance.json`.

## Low-impact reads after 0.1.10461 review

Routine polls retain only references proved against the exact reviewed source and execution context. A routine update uses one bounded Runtime.callFunctionOn for owned data, public tracker values and recorded journal data, without repeated debugger/DOM inspector/scope commands. Detached/replaced canvases and changed execution contexts invalidate this path. Polls run every eight seconds; metadata revalidates at most once per minute and static map assets every two minutes or on a town change. With no visible viewers sampling stops; the inactive connection stays open to avoid another debugger/source attachment on every return.

The first proof still costs more than a routine read. Two live routine polls measured 11–12ms end-to-end, versus about 1800ms before the change; each added one protocol command. These timings do not measure frame-time impact or establish that all stutter has been eliminated. Maximum vitals and static item metadata can lag the fast values by up to a minute.

## Live publisher replacement (2026-10-21)
Supersedes the polling and manual-refresh notes above. After one exact-source/realm attachment, the companion installs its own snapshot container and a uniquely named Runtime binding. It does not replace game functions or register a game update hook. A bounded local callback copies the already reviewed own-player, public tracker, recorded journal and own location fields about every two seconds. It prefers browser idle time; a 1.5-second idle timeout prevents starvation while busy or hidden. Snapshots arrive as binding events. Routine dashboard reads use the Node-side snapshot and send no inspector commands. There is no minute-based retained-reader expiry or timer-based static-map reinspection. Scene/context changes still require setup again.
The scheduler ends when the canvas detaches, its unique binding disappears, a scene changes, or its copy fails. Graceful reader close removes its binding. Payloads are size-limited and accepted only from the matching execution context and binding name. Actual capture timestamps are preserved, including when a callback is delayed. Initial source inspection can still cause a one-time hitch; this change does not establish zero frame impact.
Deployment evidence: work/idle-push-deployed-proof.json. Focused scheduler tests verify busy-slot deferral, idle timeout fallback, removal/detach cleanup, exact snapshot time, correct health maximum and zero protocol commands during warm reads.

## Automatic compatibility resolution (2026-10-21)
Dashboard compatibility no longer depends only on a manually added build hash. Unknown builds are resolved from unique source structures: owner singleton and its direct host import, health/magicka helper shapes, pure map lookups, public tracker constructor schema, recorded quest manager, own movement/camera and public town-map bindings. The world-mode getters must remain simple field returns. Exact-source hashes are generated for the resolved profile, then the existing active canvas listener, executed host, module import, execution-context and owner checks still run. Ambiguous or changed structures fail closed. Resolution is cached for the proven context; the live publisher remains unchanged.
Verified against saved loaded sources for 0.1.10461 and 0.1.10530, plus simulated asset renames and unrelated changes. Negative tests reject ambiguous owner definitions, changed public tracker schema, changed mode getter behavior and a missing direct player import. Source-only tests cannot establish a loaded character; the current game's normal host proof is still required when the user starts it.

## Dashboard usability and performance update
Objective town view frames the player and a confirmed destination together, with a whole-town toggle, fixed bearing, snapshot age, nearby numbered services and a marked entrance only when its coordinates are confirmed in the same town frame. Cached map anchors convert fresh native-world positions outside the game. Hidden map panels do not redraw and town image surfaces are cached.
Equipment uses the game's classic/RRI item sprites and material palette rules, cached locally. All currently worn items were verified with genuine icon URLs; unsupported items use a neutral placeholder rather than unrelated reference pictures. Clothing occupies paired armour cells; paired accessories and light occupy one fixed row with hover names/comparisons. Upgrade arrows remain conservative and slot comparisons are cached.
The installed publisher includes automatic backoff: copies above 4 ms increase the interval up to 10 seconds, and six inexpensive copies allow gradual recovery toward 2 seconds. The performance badge reports interval and copy cost, not FPS. Initial static artwork may be cached using idle-time chunks; normal live snapshots add no inspector calls. The desktop executable/shortcut, dashboard favicon and header use the user-supplied dragon image.
Validation: 32 focused tests passed; embedded executable/19 HTTP asset checks passed; actual executable icon extracted and verified. Live checks in work/priorities-deployed-proof.json recorded all 20 worn-item icons, normal guard status, 0.6–0.7 ms copy samples and unchanged inspector count after attachment. Visual proof: outputs/dashboard-updated-verified.png. No game controls were used.

## Inventory sorting, bonus search and quiet alerts
The dashboard now sorts by equipped first, name, base value, stack weight, condition and conservative upgrade comparison. Unknown numeric values sort last. Tokenized search matches known item names, descriptions and affix resistance/attribute/skill names, including numeric skill identifiers; unidentified magical data is excluded. Sorting and alert preferences persist locally. Search input is debounced and sorting reuses cached comparisons.
Quiet alerts are browser-local snapshot processing only. They have no fetches, game commands, sound or OS notifications. Thresholds: health <=30% (reset >=45%), equipped weapons/armour condition <=20% (reset >=30%), carrying >=90% (reset <80%, only when evidence is complete). Current warnings can be dismissed; repeat crossings are subject to a two-minute cooldown. Stale/unknown data cannot trigger an alert. A Connection checkbox disables alerts.
Carrying evidence is calculated in Node from fields already present in snapshots and is deliberately incomplete when exemption flags, item weights or bag handling are unknown. The game reader, publisher, sampling interval and inspection protocol were not changed by this feature work.
Validation: 25 focused tests passed. UI verified real Long Blade search and lowest-condition sorting; narrow layout also verified. Live proof work/inventory-alerts-deployed-proof.json showed unchanged inspector count (95) and 0.5–0.7 ms copies. Screenshot: outputs/inventory-bonus-search-verified.png. Canonical executable and existing desktop shortcut target updated; game untouched.
